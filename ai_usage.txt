TASK 2 — Semantic checker / type checking pass (1.5 pt)
============================================================

Prompts (mine, paraphrased):
 - "давай тепер розберемо це завдання" (Task 2 description pasted)
 - "так" (confirming plan)
 - many short clarifying questions while implementing (where to add a method, whether
   a particular check was already covered by the task text, etc.)
 - "перевір чи все ми виконали по завданню 1 та 2 правильно"
 - "перевіряй дуже уважно чи виконали ми все по завданню і правильно"

What Claude proposed / I took as-is:
 - A visitor pattern: `accept(self, visitor)` added to every AST node, dispatching to
   `visitor.visit_<node>`.
 - A new `SemanticChecker` class with its own symbol table (name -> DeclNode),
   run as a separate pass between parsing and codegen.
 - The five type rules from the task: no redeclaration, no use-before-declaration, no
   assignment to non-`mut` variables, only i32->i64 widening allowed (no narrowing, no
   bool<->integer conversion in any direction), and `==`/`!=` only between two
   comparable (matching bool-ness) operands.
 - Error messages with `line:col` pointing either at the assignment/declaration site,
   or — specifically for an out-of-range constant — at the constant itself, since the
   task expects the error location to make sense to a user reading the diagnostic.

Bug we found and fixed together:
 - All 8 new `accept()` methods had been copy-pasted from `ExitNode.accept` and all
   called `visitor.visit_exit(self)` instead of their own `visit_<node>` method. Found
   by grepping the file for `visit_exit`; fixed by replacing each occurrence in order
   with the correct visit name.
 - The overflow-constant error initially reported the position of the variable name
   instead of the constant when a stand-alone literal (e.g. `i32 x { 3000000000 }`)
   didn't fit the declared width; added a specific branch in `check_assignable` for
   this case so the diagnostic points at the constant.

What I changed / verified myself:
 - Ran the compiler against 9 different invalid programs (bool arithmetic, narrowing
   on decl and on assign, bool<->int in both directions, overflow constant, bool vs
   int compare, malformed `==`, chained comparison, operator after `exit`,
   self-reference in initializer) and confirmed every message and line:col matched
   what the task expects.

TASK 3 — LLVM codegen: widening, comparisons, bool exit (1 pt)
============================================================

Prompts (mine, paraphrased):
 - "давай тепер розберемо це завдання" (Task 3 description pasted)
 - "так" (confirming plan)
 - "дай повний код на run_tests.py"
 - "перевіряй уважно файл тепер"
 - "де саме його вставити"

What Claude proposed / I took as-is:
 - Removed the old ad-hoc `symbols` dict used during codegen; `DeclNode` now stores
   its own alloca pointer (`self.ptr`), and `VarNode`/`AssignNode` read/write through
   `self.decl.ptr`, set earlier by the semantic pass.
 - A single `coerce(builder, value, have, want)` helper that emits `sext` only for
   i32->i64, used in the 5 places that need it: variable initializer, assignment,
   both operands of `+ - *`, both operands of `== !=`, and the exit value.
 - `LLVM_TYPES` mapping `i32/i64/bool` to `ir.IntType(32/64/1)`.
 - `BinOpNode` codegen split into two paths: arithmetic (coerce both sides to the
   already-computed `node.type` from the semantic pass) vs. comparison (coerce both
   sides to the wider of the two, then `icmp_signed`).
 - `ExitNode` codegen split on bool vs integer: integer exit values are widened to
   i64 and printed with `%lld`; bool exit values are turned into `"true"/"false"`
   global string constants via `builder.select` and printed with `%s`.
 - A completely new Python test runner (`run_tests.py`) replacing the old bash loop,
   which compiles + runs each `tests/**/*.txt` with `lli`, compares stdout/stderr
   against a `.expected` file, and separately diffs `--ast` output against `.ast`
   snapshots.

Bug we found and fixed together:
 - While hand-editing `main_cli()` in `nano` to add CLI argument validation, the
   whole `try: lex/parse/SemanticChecker ... except CompileError` block got
   accidentally deleted. Found by asking Claude to re-read the whole file carefully;
   Claude pointed out exactly where the block used to sit and gave me the code to
   restore it.
 - Closed the remaining open code-review items about CLI argument handling: unknown
   flag now reports a clean error (`args[0].startswith("-")`) instead of a Python
   traceback; refuses to run if the output path equals the input path (prevents
   overwriting the source file); wrapped file-opening in `try/except OSError` for a
   one-line error instead of a traceback on a missing input file.

What I changed / verified myself:
 - Re-ran the full Practice 2/3 regression suite (32 old tests) plus the Task 1
   worked example and the bool-exit example after every codegen change, to make sure
   nothing that used to pass broke.
