# Тиждень 10: оптимізації, ABI та лінкування

## Лекція 10.1. Оптимізації
- Правило as-if: оптимізація зберігає все, що програма друкує, читає і повертає; доказ — однаковий вивід з прапорцем і без.
- Мертвий код: недосяжний (після return, умова ніколи не істинна) і мертвий (обчислений, але не прочитаний). Одне видалення робить мертвим наступне. Лічильники використань на декларацію, а не на ім'я; раунди повторюються; дві функції, що викликають лише одна одну, не дійдуть до нуля (цикл, як у reference counting).
- Бібліотеки: функції з external лінкуванням `globaldce` залишає; у програмі зовні викликається лише `main` (internalize + globaldce); у бібліотеці всі експортовані символи лишаються.
- Інлайнінг: тіло замість виклику; виграш у тому, що тіло зустрічається зі значеннями викликача (t*t + 20 ≥ 20, тому x == 15 ніколи не істинне); геттери безкоштовні лише завдяки інлайнінгу.
- Час проти розміру (таблиця): функція з одним викликом — швидше й не більше; зі 100 викликами — швидше, але більше; outlining — повільніше, але менше (-Oz).
- Підстановка (t → 8) і згортання (8 + 10 → 18) живлять одне одного; constexpr; крос-компіляція: константа обчислюється у форматі цільової платформи програмно (fp128, x86_fp80).
- Живий приклад -O0 проти -O1 зводить main до `ret i32 324`.
- opt на вашому IR: mem2reg (слоти → регістри), instcombine (a + a → shl), dce.
- SSA: кожне присвоєння дає нове ім'я; phi вибирає значення за блоком-попередником; ваш компілятор phi не генерує, його будує mem2reg.
- Front end / mid end / back end (таблиця): що де робиться.
- Stage 3: інлайнінг на дереві (параметри → локальні декларації, exit → значення, рекурсивні функції не інлайнити), у README фрагмент IR до/після.

## Лекція 10.2. ABI та лінкування
- Після llc: об'єктний файл; `nm`: T — визначено тут, U — визначено деінде (printf, scanf); модуль лише оголошує printf і scanf, і ніхто не перевіряє, що вони існують.
- Лінкер знаходить printf у libc.so.6 і записує залежність; завантажувач (ld-linux) на старті підключає бібліотеку.
- ABI: розміри й вирівнювання, конвенція викликів (AArch64: x0–x7; x86-64: rdi, rsi…), як передається структура, імена символів (name mangling). Невідповідність — це crash, а не помилка. API проти ABI.
- printf і scanf як декларації: `...` — довільні аргументи, викликана функція довіряє рядку формату; clang бачить рядок формату й попереджає, LLVM і лінкер бачать лише `i8*, ...`.
- -L каже лінкеру, але не завантажувачу: LD_LIBRARY_PATH, rpath.
- Версії символів: `@@` — за замовчуванням, `@` — для старих програм; стара версія лишається, бо бібліотека лише росте.
- Статичне проти динамічного (775 КБ проти 70 КБ); embedded, користувацькі системи, пакетні менеджери (Pre-Depends).
- FFI: усі говорять ABI мови C (ctypes, JNI, extern "C", cgo).
- Навмисне порушення ABI: `%lld` замість `%d` у visit_read — компілюється, лінкується, дає правильну відповідь випадково, а з -O1 падає; AddressSanitizer називає причину.
- Структура через межу: ваш компілятор передає Point по полях, C — одним 64-бітним регістром; LLVM не застосовує C ABI, це робить front end.

## Що вимагає завдання

Зараз `read()` і `print` викликають `scanf` і `printf`, які компілятор оголошує сам. З `extern` програма оголошує C-функцію сама:

```
extern fn abs := (i32 v) -> i32
```

- Рядок має сигнатуру й **не має тіла**. Тіло знаходить лінкер: `abs` у libc або функція з твого `.c` файлу, переданого в `clang`.
- Стоїть у секції функцій: після структур, перед інструкціями. Викликається як звичайна глобальна функція (з інструкцій, функцій і методів).
- В IR це `declare i32 @"abs"(i32 %".1")` під **чистим C-ім'ям**, без префікса `fn.`, який є у твоїх власних функцій.
- Лінкер зіставляє лише імена, а не типи. Неправильне оголошення дасть сміття або crash (як `%lld` у лекції 10.2). Тому чекер пускає лише те, що генератор може гарантувати: `i32` (це C `int`) та `i64` (`long long`).
- `struct` та `bool` не проходять. C передає `struct Point` одним 64-бітним числом, а ти по полях. `bool` на різних платформах означає різне (`zeroext` на x86-64, простий `i1` на Linux aarch64, тобто на твоїй машині).

## Крок 5. Чекер: що можна передати в C

**Навіщо він потрібен.** Лінкер зіставляє лише імена, а не типи. Тому неправильне оголошення нічого не покаже при збірці, а під час запуску дасть сміття або crash. Це та сама ситуація, що й `%lld` проти `int` у лекції 10.2. Чекер має відхиляти все, чого твій генератор не вміє передати за правилами C.

Чекер перевіряє два види речей:
1. **Типи.** Дозволені лише `i32` (C `int`) та `i64` (C `long long`). `bool` і структури заборонені, бо C передає їх інакше, ніж ти.
2. **Імена.** Ім'я не може збігатися з тим, що модуль уже використовує, інакше в IR вийшло б два об'єкти з одним іменем.

Перевірки в твоєму коді найлогічніше робити в `collect_signatures`: там уже перевіряються дублікати й імена структур для всіх функцій.

**а) Константа з іменами модуля.** Під рядком `BUILTIN = ("i32", "i64", "bool")` на початку файлу додай:

```python
MODULE_NAMES = ("main", "printf", "scanf", "fmt", "fmt_bool", "true_str", "false_str")
```

Перші три це те, що завдання називає прямо. Решта чотири моє додавання, і ти вирішуєш, чи лишати їх. Це глобальні змінні, які `main_cli` створює в модулі до генератора. Якщо хтось оголосить `extern fn fmt`, то, на мою думку, `llvmlite` кине `DuplicatedNameError` з traceback замість помилки з рядком і колонкою. Це я не перевіряв, ми побачимо це в кроці з генератором. Якщо не хочеш виходити за рамки завдання, залиш у кортежі лише перші три.

## Крок 7. Оптимізатор

**Де саме падає.** `effectful_fns` проходить по кожній функції програми й обходить її тіло, щоб знайти виклики та побічні ефекти. У `extern` тіла немає (`None`), і обхід падає. Тіло `own_effect(f.body)` у наступному рядку впало б так само.

**Що має бути натомість.** Завдання каже: невикликаний `extern` видаляється, як будь-яка глобальна функція, а виклик `extern` зберігається, бо його тіло в C може щось друкувати. Тож для `extern` ми не обходимо тіло, а одразу вважаємо, що він має побічний ефект. Правило «коли сумніваєшся, лишай» діє й тут: компілятор не бачить C-коду, тому не може довести, що там нічого не відбувається.

Решту не чіпаємо, бо вона вже працює:
- `UseCounter` рахує виклики за `id(n.fn)`, а `extern` це той самий `FnNode`, тож невикликаний отримає 0 і буде видалений;
- `children()` ми перевизначили на параметри, тому `Pruner` та `dump` не спіткнуться;
- `has_effect` бачить виклик функції з `effects` і не видаляє оголошення, яке його містить.

## Крок 10. Тести для `extern`

Лишилося дві групи: програма лише з libc у `tests/ok` і дев'ять програм у `tests/err`. Файли створюємо через `printf`, а не heredoc: так вставка в терміналі не розсиплеться, як було з `geometry.txt`.

### а) `tests/ok`: libc-функції, що працюють і під `lli`

Завдання вимагає `abs` та `llabs` з `i64`. Мінус у мові немає, тому від'ємні числа збираємо як `0 - 7`:

```bash
printf 'extern fn abs := (i32 v) -> i32\nextern fn llabs := (i64 v) -> i64\ni32 a{0 - 7}\ni64 big{0 - 3000000000}\nprint(abs(a))\nprint(llabs(big))\ni64 r{llabs(big) + abs(a)}\nexit r\n' > tests/ok/extern_libc.txt
printf '7\n3000000000\nProgram exit with result 3000000007\n' > tests/ok/extern_libc.expected
```

Що перевіряє програма:
- `abs` приймає й повертає `i32`, а `llabs` приймає й повертає `i64`;
- `0 - 3000000000` це `i32` мінус `i64`, тобто `i64`;
- виклики стоять і в `print`, і в ініціалізаторі;
- `r = 3000000000 + 7 = 3000000007`, число більше за `i32`, тож перевіряється і ширина результату.

Перевір напряму через `lli`, як вимагає завдання:

```bash
python3 compiler.py tests/ok/extern_libc.txt /tmp/ok1.ll && lli /tmp/ok1.ll
```

Очікую `7`, `3000000000`, `Program exit with result 3000000007`.

## Граматика: немає `extern`

Це головне. Правила для `extern` у ній немає, а `program` каже `{ fn }`. За такою граматикою програма з `extern` невалідна, хоча компілятор її приймає. Треба додати правило й дозволити його в `program`.

Спершу знайди файл (я не знаю його імені):

```bash

```

Підстав знайдене ім'я замість `GRAMMAR_FILE` у двох командах:

```bash
sed -i 's#{ fn } { statement } exit#{ fn | extern_fn } { statement } exit#' GRAMMAR_FILE
sed -i '/^fn  *::=/a extern_fn ::= "extern" "fn" ident ":=" "(" [ param { "," param } ] ")" "->" type NL' GRAMMAR_FILE
grep -n "extern" GRAMMAR_FILE
```

Очікую два рядки: `program ::= { struct } { fn | extern_fn } { statement } exit` і нове правило `extern_fn` одразу під `fn`. Тіла в нього немає, тому воно закінчується на `NL`.

## Що означає кожен пункт

**1. Найкорисніші можливості чи ідіоми курсу.** Йдеться про те, що тобі справді допомогло: в роботі над компілятором або в розумінні мов загалом. Корисність потрібно обґрунтувати одним твердженням, яке можна перевірити, а не просто назвати тему.

**2. Що розкрито недостатньо.** Це критика курсу: де лекція чи практика дала мало, щоб зробити наступний крок. Вкажи, яка саме тема (лекція, практика) і чого саме не вистачило.

**3. Щонайменше три приклади, що найбільше здивували.** Тут «щонайменше три»: два приклади не зарахують. Зверни увагу на слово «здивували», а не «було складно». Це має бути щось, що спростувало твоє очікування. Приклади мають стосуватися мов і компіляторів, але не обов'язково твого коду.

**4. Що досі незрозуміло.** Чесне запитання до себе й до курсу. Чим точніше сформульовано непорозуміння («не розумію, чому…», «не бачу різниці між… і…»), тим краще. Загальне «складно» не зараховується.

**5. Інші ідеї та пропозиції щодо змісту курсу.** Вільний пункт: що додати, прибрати, змінити в порядку чи в практиках. Конкретність тут теж виграє.
